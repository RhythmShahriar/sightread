# Sightread benchmark

Generated by go run -tags testbed ./testbed/bench. Do not edit.

We wrote Sightread and the testbed, so read this as a regression suite with a scoreboard, not an independent review. Every bad scenario is something we built Sightread to catch, modelled on real incidents (the 2026 WordPress.org plugin backdoor, Shai-Hulud). Every good scenario is a benign update that must stay quiet. The other tools run on the same fixtures, which are not real packages. A real attacker who reads our detectors can write code they miss; Sightread lowers the risk of an update, it does not prove an update is safe.

## Known gaps

What this board does not cover:

- Logic that waits for a date, a domain or a visitor count; code fetched at run time from a server that serves clean code to scanners: the fixtures cannot show what a payload does later.
- Obfuscation beyond the layered decodes in b05 and b23, compiled assets and binaries: unanalysed is reported, not what they do.
- Evasions written against the published detectors: the metamorphic fuzz targets cover rewrites of known shapes only.
- Owner changes that keep the same account; sales WordPress.org does not show (PRD 18 point 6).
- Typosquats of niche packages that are not on the popular-names list.
- Case and Unicode collisions on macOS and Windows file systems: e05 runs on Linux, where only the report is checked.
- Windows-only behaviour (e13) unless the benchmark runs on Windows.
- SARIF fingerprint stability, HTML escaping in a real browser and watch alert dedupe: covered by golden and unit tests, not by this board.
- Lockfiles Sightread does not read (yarn.lock, bun.lockb): checked by unit tests for the E4 and E8 messages only.
- Real releases: the fixtures are not real packages; the owner-run real-release section below is the only measure of noise beyond them.
