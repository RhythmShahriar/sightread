# Changes: detect lane

What users see from the detectors, the explain text and the data packs.
The full reference of every signal (when it fires, false alarms, how to
review, incidents) is `docs/signals.md`, generated by
`go run ./detect/cmd/signalsdoc`; the wiki's
`Sightread-Signal-Reference.md` is made from it with one anchor per ID.

## Signals

Titles describe behaviour, never intent. `approved-version-changed` is
raised by the allow list check (package policy), every other ID by a
detector. `integrity-mismatch`, `version-republished`,
`approved-version-changed`, `known-malicious` and `archive-path-escape`
can never be ignored, allowed or lowered.

Every finding carries the signal's advice line (`advice` in
`detect/explain/<id>.yaml`); `integrity-mismatch` names the source in
it ("Someone between you and wordpress.org changed it, or the release
was edited; don't install this copy.", with "the npm registry" or
"Packagist" for the other ecosystems). A known-vulnerable advisory the
update fixes is info with the title `fixes <id>` and the advice
`This update fixes it.`

## Context wording

`demoted` says why a detector lowered a finding (exact text):

| Signal | Demoted | Level |
|---|---|---|
| `outbound-new-domain`, `unicode-hidden` | `not in code (comment, docs or tests)` | info |
| `outbound-new-domain` | `listed in signals.domains_ok` | info |
| `outbound-new-domain` | `the package's own host` | info |
| `outbound-new-domain` | `known host` (the shipped known-safe list) | info |
| `secret-added` | `test or fixture path` | info |
| `secret-added` | `documented example value` | info |
| `unicode-hidden` | `translation file` | info |
| `archive-link`, `archive-collision` | `in the installed version's archive, not the candidate's` | info |
| `dependency-new` | `development dependency` | info |
| `size-jump` | `new languages/ folder` (each new `languages/`, `vendor/` or `dist/` folder named, comma separated) | info |

`raised_by` from a detector: `rest-open-route` is high with `raised_by`
holding the sorted IDs of the new code signals in the same file
(`admin-user-create`, `admin-user-hidden`, `decode-exec`,
`eval-dynamic`, `input-unserialize`, `remote-fetch-exec`,
`write-outside-package`). The other context rules of PRD 12.2 (owner
change raises, same function raises, vendored paths demote with
`vendored path`) belong to the scorer.

## Data packs

`rhythm-sightread update --json` reports two packs:

| Name | Holds | Version |
|---|---|---|
| `sightread-names` | popular names: 1,500 WordPress.org plugins, WordPress.org themes, npm and Packagist packages | the release it came from (`1.0.1`), or the embedded pack's date (`2026.10.26`) |
| `sightread-signals` | the rule files of `detect/code/rules`, the known-safe hosts (wordpress.org, w.org, gravatar.com, fonts.googleapis.com, fonts.gstatic.com, schema.org, w3.org) and the pack's version marker | the same |

`sha256` is the hash of the pack's release asset bytes
(`sightread-names.json`, `sightread-signals.tar.gz`).

## `rhythm-sightread update`

1. Finds the latest Sightread release on GitHub (`SIGHTREAD_GITHUB_API`,
   then `RHYTHM_GITHUB_API`, then api.github.com).
2. Checks the Sigstore signature over `checksums.txt`
   (`checksums.txt.sigstore.json`): the shared `release-go.yml` workflow
   at `refs/heads/master` building `RhythmShahriar/sightread`.
3. Downloads both assets, checks each against `checksums.txt` and
   parses it.
4. Only then writes them atomically to
   `<cache>/data/` (`config.CacheDir("sightread")/data`, mode 0700) with
   `packs.json`, then prints one line per pack, for example
   `sightread-names 1.0.1 (data 2026.11.02) verified`, then the kit's
   `<name> <version>` lines.

Offline (`RHYTHM_OFFLINE`) or on any failure nothing is written, what
was there stays and the command exits 3 with
`rhythm-sightread: update failed: <reason>`. Reasons include:

- `the release signature can't be checked: this build has no Sigstore verifier, so no pack was downloaded`
- `release 1.0.1: <signature error>` (from kit update, fails closed)
- `release 1.0.1: sightread-names.json has sha256 <hex>, checksums.txt says <hex>`
- `release 1.0.1 has no sightread-names.json`, `release 1.0.1: checksums.txt does not list sightread-names.json`
- `downloading sightread-names.json: <error>`; only https is used, or http to 127.0.0.1 for tests

`update --pin sightread-names=1.0.1,sightread-signals=1.0.1` downloads
those releases' assets the same way; a pinned pack is used even when the
embedded one is newer. A pin equal to the version already in force
prints `sightread-names 2026.10.26 is already in place` and needs no
network. Errors, all exit 3:

- `--pin: no pack is called "x" (the packs are sightread-names and sightread-signals)`
- `sightread-names 2026.10.01: not a Sightread release version; this machine has 2026.10.26`
- `finding the release: <error>` (no such release)

On every run a cached pack is used only when it still hashes to the
recorded sha256, parses cleanly and is newer than the embedded one (or was
pinned); anything else falls back to the embedded pack without a
message. `--no-signal-updates` (run calls `data.Default().UseEmbedded(true)`)
makes the names, the known-safe hosts and the rules come from the
embedded files only. The packs are data: nothing in them is ever run.

## Release prep

- `go run ./data/gen` (network, by hand only) refreshes
  `data/names/*.json` from WordPress.org, the npm registry search and
  Packagist and prints each file's sha256.
- Bump `data/signals/pack.json` when `detect/code/rules` or
  `data/domains-ok.json` changes.
- `go run ./data/gen --pack` (no network) writes
  `data/release/sightread-names.json` and
  `data/release/sightread-signals.tar.gz` deterministically;
  `TestReleasePacksCurrent` fails while they are stale.
- `go run ./detect/cmd/signalsdoc` rewrites `docs/signals.md`;
  `TestSignalsDocCurrent` fails while it is stale.
